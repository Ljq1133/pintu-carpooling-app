# C 组当前进度与后续工作

## 1. 当前状态

B 组乘客端 MVP 已合并到 `main`，C 组司机端和管理端已通过共享 Mock 平台与乘客端接通，不再维护互相独立的订单副本。

当前可以在同一个前端页面完成以下跨端流程：

1. 乘客发布拼车需求。
2. 司机端收到请求并同意或拒绝。
3. 司机开始行程、确认到达。
4. 管理端实时查看订单状态。
5. 乘客完成支付，订单变为已完成。
6. 管理端审核车辆并调整信用分。
7. 低信用乘客不能发单，低信用司机不能发布行程或接单。

## 2. 已完成内容

### 2.1 司机端

- 查看司机资料、车辆和已发布行程。
- 发布司机行程。
- 查看来自乘客端的顺路请求。
- 同意或拒绝乘客请求。
- 开始行程并确认到达。
- 根据车辆审核状态和信用状态限制操作。

### 2.2 管理端

- 实名审核和车辆审核。
- 查看由乘客端产生的实时订单。
- 查看订单从已确认、履约中、待付款到已完成的状态变化。
- 调整乘客和司机信用分。
- 将车辆审核结果同步到司机端。

### 2.3 跨端联调

- 已建立统一共享状态和 C 组 API Adapter。
- 已删除 C 组重复维护的司机行程、候选乘客数据。
- 已增加跨端集成烟测脚本。
- 已补充 B/C 跨端集成说明和接口需求文档。

## 4. 下一阶段建议

### P0：等待 A 组接口后替换 Mock

保持页面调用 `driverApi`、`adminApi` 和 `passengerApi`，将 Mock 实现逐步替换为真实 HTTP 请求，避免再次改动页面业务逻辑。

### P1：与架构测试组确认状态契约

重点确认：

- 订单、行程、匹配请求是否分别建表。
- 同意请求后由哪一端创建订单。
- 开始行程、到达和支付是否允许重复调用。
- 取消订单时座位数和信用分如何回滚。
- 司机与乘客低信用限制的阈值和恢复规则。

### P2：补充异常流程

- 司机拒绝后乘客重新选择行程。
- 行程满员后停止接收请求。
- 订单取消与退款。
- 请求超时自动失效。
- 网络失败后的重试和提示。
