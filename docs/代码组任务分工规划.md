# 代码组任务分工规划

## 一、当前项目背景

课程要求中与代码组直接相关的内容包括：

- 制定编码规范
- 进行程序和代码编写
- 对单元模块进行语句覆盖和路径测试
- 进行运行集成和确认测试
- 完成软件项目运行展示和功能展示

课程报告提交截止时间为：**2026 年 6 月 21 日之前**。

## 二、开发目标

代码组应优先完成一个可以运行、可以展示、可以支撑报告截图和测试说明的最小可交付版本。

建议优先实现以下核心链路：

> 乘客登录并发布订单 -> 系统推荐司机行程 -> 乘客向司机发起拼车请求 -> 司机同意 -> 双方确认订单 -> 行程完成 -> 乘客付款模拟 -> 乘客评价 -> 管理后台查看订单状态变化

这个链路能够覆盖项目中最重要的业务逻辑，包括：

- 乘客发单
- 司机发车
- 行程匹配
- 双向同意
- 订单状态流转
- 支付模拟
- 评价与信用分
- 后台订单监控

## 三、总体分工原则

建议不要简单按“前端 / 后端 / 数据库”拆分，否则容易出现某一部分卡住后其他人无法继续联调的问题。

更合理的方式是：

- 每个人负责一个相对完整的业务模块
- 每个人都能产出可演示功能
- 核心接口和数据结构由一人统一维护

| 成员 | 主要负责模块 | 具体任务 | 最终展示点 |
|---|---|---|---|
| A | 核心后端与数据负责人 | 数据库表设计；用户、订单、行程、匹配请求等实体设计；登录注册接口；乘客订单和司机行程 CRUD；订单状态机；基础 API 文档 | 后端能够支撑完整业务流程 |
| B | 乘客端 + 匹配负责人 | 乘客登录后的乘车页面；发布拼车需求；展示推荐司机行程；向司机发起拼车请求；查看订单详情；乘客侧协商、确认、取消、付款、评价操作；简化匹配算法实现 | 乘客“发单 - 匹配 - 确认 - 付款 - 评价”流程 |
| C | 司机端 + 管理端 + 联调负责人 | 司机发布行程；展示推荐乘客需求；司机接收和同意乘客请求；车辆信息管理；简单后台管理页面；订单看板；实名/车辆审核模拟；信用分和黑名单管理模拟；集成测试和演示数据准备 | 司机“发车 - 接单 - 履约”流程 + 管理后台看板 |

## 五、成员 A：核心后端与数据负责人

### 1. 主要职责

成员 A 负责整个项目的后端基础能力和数据结构，保证 B、C 两位成员可以基于稳定接口进行开发。

### 2. 具体任务

- 设计核心数据库表
- 编写实体类 / 数据模型
- 实现登录、注册、用户信息接口
- 实现乘客订单的新增、查询、修改、取消
- 实现司机行程的新增、查询、修改、取消
- 实现订单状态流转逻辑
- 实现匹配请求的创建和处理
- 整理基础 API 文档
- 协助 B、C 完成接口联调

### 3. 建议优先设计的数据表

- `User`：用户表
- `DriverProfile`：司机认证信息表
- `Vehicle`：车辆信息表
- `PassengerOrder`：乘客拼车需求表
- `DriverTrip`：司机行程表
- `MatchRequest`：匹配请求表
- `Order`：最终订单表
- `Payment`：支付记录表
- `Review`：评价表
- `Complaint`：申诉工单表

### 4. 重点注意

订单状态流转要与报告中的“订单生命周期”保持一致。

建议状态包括：

- `待匹配`
- `协商中`
- `已确认`
- `履约中`
- `待付款`
- `已完成`
- `已取消`

## 六、成员 B：乘客端 + 匹配负责人

### 1. 主要职责

成员 B 负责乘客侧核心功能，让用户能够完成从发布拼车需求到订单完成的主要流程。

### 2. 具体任务

- 实现乘客登录后的主页面
- 实现定位信息展示，可以先使用模拟定位数据
- 实现出发地、目的地、出发时间等信息输入
- 实现乘客发布拼车需求
- 调用匹配接口，展示推荐司机行程
- 实现乘客向司机发送拼车请求
- 实现乘客订单列表
- 实现订单详情页
- 实现乘客确认订单、取消订单、修改订单
- 实现付款模拟
- 实现订单评价

### 3. 简化匹配算法建议

为了保证项目能按时完成，匹配算法可以先采用简化规则：

- 出发地相同或相近
- 目的地相同或相近
- 出发时间在允许范围内
- 司机剩余座位数大于 0
- 司机信用分达到最低要求

如果需要体现“顺路度”，可以先用百分比字段模拟，例如：

- 80% 以上：推荐
- 60% - 80%：可选推荐
- 60% 以下：不推荐

### 4. 最终展示效果

乘客侧至少应能展示：

- 发布拼车需求
- 查看推荐司机行程
- 发起拼车请求
- 查看订单状态变化
- 完成付款和评价

## 七、成员 C：司机端 + 管理端 + 联调负责人

### 1. 主要职责

成员 C 负责司机侧业务流程、简单后台管理系统，以及最终联调和演示数据准备。

### 2. 司机端具体任务

- 实现司机登录后的开车页面
- 实现司机车辆信息选择
- 实现司机发布行程
- 展示系统推荐的乘客订单
- 实现司机向乘客发起接单意向
- 实现司机接收乘客请求
- 实现司机同意或拒绝请求
- 实现司机行程列表
- 实现行程详情页
- 实现司机确认上车、确认下车、完成行程等操作

### 3. 管理端具体任务

管理端可以简单实现，不需要做得过于复杂，重点是支撑报告和功能展示。

建议实现：

- 用户实名审核列表
- 车辆资质审核列表
- 订单状态看板
- 按状态查询订单
- 信用分管理模拟
- 黑名单管理模拟
- 申诉工单查看和处理模拟

### 4. 联调与演示数据

成员 C 同时负责准备最终展示所需的模拟数据，例如：

- 乘客账号
- 司机账号
- 管理员账号
- 若干乘客订单
- 若干司机行程
- 已匹配订单
- 已完成订单
- 待审核车辆信息
- 申诉工单

## 九、需要及时和架构测试组确认的问题

开发过程中，如果遇到以下问题，应及时联系架构测试组确认：

- 订单状态名称是否需要严格按照报告中的五大生命周期分区
- 乘客和司机“双向同意”的具体触发方式
- 匹配算法是否必须真实计算路径重合度，还是可以用模拟顺路度
- 支付功能是否只做模拟
- 地图定位是否只做模拟
- 信用分加减规则是否需要完整实现
- 管理后台需要做到什么程度
- 测试组需要代码组提供哪些接口、截图和测试数据

## 十、今晚会议建议议程

**1. 技术栈**

建议选一个开发成本低、容易联调、适合课程展示的技术栈：

- 前端：Vue 3 + Element Plus
- 后端：Spring Boot
- 数据库：MySQL
- 接口风格：RESTful API
- 地图/定位：先用模拟数据，不接真实地图 API
- 支付：只做模拟支付，不接真实支付接口
- 登录认证：先做普通账号密码登录，验证码、人脸识别等作为报告扩展说明

这样比较适合 3 个人短期开发，也方便截图、写报告和做测试。

**2. 是否只做最小可交付版本**

建议：**先只做最小可交付版本 MVP**。

原因是课程重点不是商业级完整系统，而是体现软件工程流程：需求、设计、编码、测试、展示。

MVP 必须跑通这条主线：

> 乘客发单 -> 系统匹配司机行程 -> 乘客发起请求 -> 司机同意 -> 双方确认 -> 行程完成 -> 模拟付款 -> 评价 -> 后台查看订单

其他功能，如真实地图、真实支付、短信验证码、虚拟手机号、一键报警，可以写进报告作为扩展设计，不作为第一阶段代码重点。

**3. 三人具体分工**

建议这样定：

| 成员 | 分工                       |
| ---- | -------------------------- |
| A    | 后端与数据库负责人         |
| B    | 乘客端与匹配功能负责人     |
| C    | 司机端、管理端与联调负责人 |

具体来说：

A 负责数据库表、后端接口、订单状态流转、用户登录注册、数据增删改查。

B 负责乘客端页面，包括发布拼车需求、查看推荐司机、发起请求、查看订单、付款、评价。

C 负责司机端和简单后台，包括发布司机行程、查看乘客请求、同意接单、确认行程完成、后台订单看板、审核和信用分模拟。

**4. 数据库核心表**

建议先定这些核心表：

| 表名              | 用途                                 |
| ----------------- | ------------------------------------ |
| `user`            | 用户账号信息，包括乘客、司机、管理员 |
| `driver_profile`  | 司机认证信息                         |
| `vehicle`         | 车辆信息                             |
| `passenger_order` | 乘客发布的拼车需求                   |
| `driver_trip`     | 司机发布的行程                       |
| `match_request`   | 乘客和司机之间的匹配请求             |
| `order_record`    | 双方确认后形成的正式订单             |
| `payment`         | 模拟支付记录                         |
| `review`          | 订单评价                             |
| `complaint`       | 申诉工单                             |
| `credit_record`   | 信用分变动记录                       |

如果时间不够，可以合并简化：

- `driver_profile` 和 `vehicle` 可以先简化处理
- `payment` 可以只作为订单字段
- `credit_record` 可以只保留用户表里的 `credit_score`

**5. 订单状态流转**

建议统一使用下面这套状态，代码和报告都按这个写：

1. `待匹配`
   乘客发布订单或司机发布行程后，还没有匹配成功。

2. `协商中`
   一方向另一方发起请求，对方同意后进入协商。

3. `已确认`
   双方确认价格、时间、地点等信息，订单正式成立。

4. `履约中`
   双方确认上车后，行程开始。

5. `待付款`
   司机确认送达，行程结束，等待乘客付款。

6. `已完成`
   乘客付款并评价，订单结束。

7. `已取消`
   任意一方取消订单，订单终止。

重点原则：

- 任何订单必须遵循“双向同意”
- 已确认后如果修改订单，需要重新回到“协商中”
- 已确认后取消订单，可以扣信用分
- 支付只由乘客侧触发
- 评价在支付完成后进行

**6. 接口文档由谁维护**

建议由 **A 维护接口文档**，因为 A 负责后端和数据库，最清楚接口参数和返回值。

但是 B、C 也要负责补充自己页面需要的接口需求。

安排方式：

- A 建一个统一接口文档，例如 `接口文档.md`
- 每新增一个接口，A 及时写入接口路径、请求方式、参数、返回值
- B、C 如果需要新接口，先在群里提出，再由 A 确认实现
- 接口文档要和实际代码保持一致，不能只写报告用的假接口

接口文档至少包含：

- 登录注册接口
- 乘客订单接口
- 司机行程接口
- 匹配请求接口
- 正式订单接口
- 支付接口
- 评价接口
- 管理后台接口

**7. 需要向架构测试组提问的问题**

建议今晚整理出这些问题发给架构**测试**组：

1. 订单生命周期是否就采用：待匹配、协商中、已确认、履约中、待付款、已完成、已取消？
2. 匹配算法是否允许先用模拟顺路度，而不是接真实地图 API？
3. 支付功能是否可以只做模拟支付？
4. 定位功能是否可以只使用模拟位置数据？
5. 管理后台需要做到什么深度，是简单订单看板即可，还是必须包含审核、申诉、信用分？
6. 信用分扣分规则是否需要具体实现，还是只展示加减分结果？
7. 测试组需要代码组提供哪些测试用例、接口、截图和核心代码片段？
8. 报告中是否要把“乘客订单”和“司机行程”区分成两个实体，还是统一叫订单？
9. 双向同意流程中，是“请求后直接协商”，还是“一方请求、另一方同意后才进入协商”？
10. 哪些功能必须真实实现，哪些功能可以作为扩展设计写入报告？

## 十一、建议的最小演示流程

最终展示时，建议使用下面这条主线：

1. 乘客登录系统
2. 乘客发布拼车需求
3. 系统展示推荐司机行程
4. 乘客向某个司机发起拼车请求
5. 司机登录系统
6. 司机查看请求并同意
7. 双方确认订单
8. 订单进入履约状态
9. 司机确认行程完成
10. 乘客进行付款模拟
11. 乘客提交评价
12. 管理员在后台查看订单状态和用户信用信息

这条流程覆盖了乘客端、司机端、后台管理端、数据库、匹配逻辑、订单状态流转和测试展示，是最适合课程设计报告和现场演示的主线。
