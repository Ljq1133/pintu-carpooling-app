## 2. B 组职责范围

B 组负责乘客端和匹配展示相关功能。

需要完成的核心流程：

```text
乘客登录
-> 发布拼车需求
-> 查看推荐司机行程
-> 向司机发起拼车请求
-> 回到乘车页等待司机确认
-> 司机同意后乘车页展示实时行程
-> 司机确认行程开始、到达目的地
-> 乘客在乘车页模拟付款
-> 乘车页展示付款完成，可选评价
-> 订单归档到订单页已完成列表
```

B 组需要完成：

- 乘客登录后的主页面
- 模拟定位信息展示
- 出发地、目的地、出发时间、乘车人数等输入
- 发布拼车需求
- 推荐司机行程展示
- 发起拼车请求
- 乘车页等待司机确认、司机拒绝、实时行程、付款完成状态
- 乘客订单列表入口
- 已完成订单行程摘要
- 乘客查看进行中实时行程信息
- 乘客取消订单
- 乘客模拟付款
- 乘客订单评价
- 简化匹配逻辑
- B 组接口需求整理
- B 组测试截图和演示数据准备

B 组不负责：

- 司机端页面
- 管理端页面
- 后端数据库
- 真实登录鉴权
- 真实地图定位
- 真实支付
- 短信验证码、人脸识别等扩展功能

## 3. MVP 交付目标

B 组 MVP 至少要能独立演示以下内容：

1. 乘客使用演示账号进入乘客端
2. 乘客填写拼车需求
3. 系统生成一条 `待匹配` 的乘客需求
4. 页面展示推荐司机行程
5. 乘客向某个司机发起拼车请求
6. 页面自动回到乘车页，展示等待司机确认动画和 `待确认` 角标
7. mock 司机拒绝后，乘车页展示简要拒绝信息并提供“重新选择司机”
8. mock 司机同意后，乘车页展示实时行程信息，订单进入 `进行中`
9. mock 司机确认行程开始、到达目的地后，乘车页更新实时状态
10. mock 司机送达后，订单仍显示为 `进行中`，但允许乘客付款
11. 乘客完成模拟付款后订单进入 `已完成`，乘车页展示付款完成页
12. 乘客可选择评价；订单页已完成列表可查看轻量行程摘要

说明：

- mock 司机同意、mock 行程开始、mock 司机送达只是为了 B 组在 A/C 未完成前独立演示闭环
- 这些 mock 操作必须和真实乘客端功能解耦
- 后续联调时，这些状态变化应改为由后端或 C 组司机端触发

### 5.1 B 组工作台入口

工作台 tab 建议：

### 5.2 乘客登录页

功能：

- 展示 PinTu Logo
- 展示演示账号
- 输入手机号 / 密码
- 点击登录进入乘客端

演示账号：

```text
passenger_demo / 123456
```

当前阶段只做本地演示，不做真实鉴权。

### 5.3 乘车发布页

功能：

- 显示模拟定位
- 上半部分预留地图 / 路线预览区域
- 输入出发地
- 输入目的地
- 出发地和目的地提供 mock 地图定位 / 搜索入口，后续可替换真实地图 API
- 选择出发时间（默认“现在出发”，使用日期和时间选择器，不让用户手动输入完整时间字符串）
- 输入乘车人数
- 可选备注
- 点击“发布拼车需求”

发布后：

- 创建一条乘客拼车需求
- 状态为 `待匹配`
- 自动展示推荐司机行程

发送拼车请求后：

- 页面自动回到乘车页
- 乘车页展示等待司机确认动画和 `待确认` 角标
- 司机拒绝时展示简要拒绝信息，并提供“重新选择司机”按钮跳回推荐页
- 司机同意后，乘车页展示地图线路占位、司机距离 / 时间、车辆、路线、费用等实时信息
- 付款完成后，乘车页展示付款完成页和简短行程信息，可选择评价但不强制

### 5.4 推荐司机页

功能：

- 展示可匹配司机行程
- 展示路线、时间、剩余座位、顺路度、信用分、价格
- 复用 UI Kit `MatchCard` 展示推荐司机
- 支持点击“发送拼车请求”
- 发送后自动回到乘车页等待司机确认

推荐规则：

- 出发地相同或相近
- 目的地相同或相近
- 出发时间在允许范围内
- 司机剩余座位数大于 0
- 司机信用分达到最低要求（当前 B 组 mock 阶段暂按 80 分）
- 顺路度不低于 60%

顺路度展示规则：

| 顺路度     | 展示含义 |
| ---------- | -------- |
| 80% 及以上 | 推荐     |
| 60% - 79%  | 可选推荐 |
| 60% 以下   | 不推荐   |

### 5.5 订单列表页

功能：

- 展示乘客所有订单
- 按状态分组或筛选
- 进行中订单作为后台流程入口，点击后回到乘车页查看当前实时状态
- 已完成订单进入历史列表
- 已完成订单可点击“订单详情”查看轻量行程摘要

建议分组：

- 进行中：`待匹配`、`进行中`
- 已完成：`已完成`
- 已取消：`已取消`

### 5.6 已完成订单详情页

功能：

- 只作为历史订单查看入口
- 展示路线、时间、人数、价格
- 展示司机和车辆信息
- 展示支付状态和评价结果
- 展示轻量行程摘要，不默认展开完整过程明细
- 不承载进行中订单的实时主流程

状态与乘客操作：

| 当前状态 | 乘客可操作                                   |
| -------- | -------------------------------------------- |
| `待匹配` | 从订单页回到乘车页查看等待或拒绝状态         |
| `进行中` | 从订单页回到乘车页查看实时行程、联系司机、导航、到达后付款 |
| `已完成` | 查看轻量行程摘要、查看评价、再次拼车         |
| `已取消` | 查看取消原因                                 |

付款和评价规则：

- 订单在支付前统一显示为 `进行中`
- mock 司机送达后，订单仍为 `进行中`，但允许乘客付款
- 付款完成后订单进入 `已完成`
- 评价必须在付款完成后提交，不再推动订单主状态

### 5.7 我的页面

功能：

- 展示乘客昵称
- 展示手机号脱敏
- 展示信用分
- 展示出行次数
- 展示节省费用
- 展示减碳数据
- 展示我的订单、钱包、消息、设置等入口

当前阶段入口可以是静态展示。

## 6. 状态流转设计

统一订单状态：

```text
待匹配
进行中
已完成
已取消
```

主流程状态流转：

```text
发布拼车需求
-> 待匹配

司机同意请求
-> 进行中

司机确认送达 / 行程完成
-> 仍显示为进行中，但允许付款

乘客付款
-> 已完成

乘客评价
-> 已完成订单补充评价信息
```

取消流转：

```text
待匹配 / 进行中
-> 已取消
```

需要注意：

- 乘客主动向司机发起拼车请求时，司机同意后无需乘客二次确认
- 若后续实现“司机主动向乘客发起接车请求”，才需要乘客确认后进入 `进行中`
- 支付只由乘客侧触发
- 评价必须在支付完成后进行，不改变订单主状态
- mock 阶段可以用本地按钮模拟司机同意、到达上车点和送达目的地
- 联调阶段司机相关状态应由 C 组司机端或后端推送

## 8. 本地业务函数设计

`localPassengerGroupStore.js` 中建议实现：

```js
createPassengerGroupState();
createPassengerOrder(form);
getRecommendedTrips(order, driverTrips);
sendMatchRequest(orderId, driverTripId);
mockDriverAccept(requestId);
mockDriverReject(requestId);
confirmPassengerOrder(orderId);
cancelPassengerOrder(orderId);
mockDriverStartTrip(orderId);
mockDriverFinishTrip(orderId);
payOrder(orderId);
submitReview(orderId, rating, comment);
```

函数职责：

| 函数                        | 职责                     |
| --------------------------- | ------------------------ |
| `createPassengerGroupState` | 初始化 B 组本地状态      |
| `createPassengerOrder`      | 创建乘客拼车需求         |
| `getRecommendedTrips`       | 根据简化规则返回推荐司机 |
| `sendMatchRequest`          | 创建乘客到司机的拼车请求 |
| `mockDriverAccept`          | 本地模拟司机同意，订单进入进行中 |
| `mockDriverReject`          | 本地模拟司机拒绝         |
| `confirmPassengerOrder`     | 预留：乘客确认司机主动接车请求 |
| `cancelPassengerOrder`      | 乘客取消订单             |
| `mockDriverStartTrip`       | 本地模拟司机确认行程开始 |
| `mockDriverFinishTrip`      | 本地模拟司机送达目的地，允许付款 |
| `payOrder`                  | 乘客模拟付款并完成订单   |
| `submitReview`              | 乘客为已完成订单补充评价 |

约束：

- 状态流转只能通过这些函数完成
- 页面组件不要直接修改订单状态
- mock 司机函数后续要能删除或替换
- 真实接口接入后，页面调用方式尽量不变

## 10. 与 A 组联调关注点

需要和 A 组确认：

1. 乘客端订单展示状态是否统一使用：`待匹配`、`进行中`、`已完成`、`已取消`
2. 乘客发布需求后，后端创建的是 `PassengerOrder` 还是直接创建 `Order`
3. 乘客发起请求后，后端是否创建 `MatchRequest`
4. 司机同意请求后，是否自动生成正式订单
5. 乘客主动发起请求时，司机同意后订单是否直接进入 `进行中`
6. 司机主动发起接车请求时，是否需要乘客确认后再进入 `进行中`
7. 进行中订单取消是否扣信用分
8. mock 司机送达后是否通过支付入口可用来表达，而不是新增付款前主状态
9. 支付是否只做模拟
10. 评价是否和付款绑定

## 11. 与 C 组联调关注点

需要和 C 组确认：

1. B 组发起的匹配请求是否能在司机端显示
2. C 组司机同意后，B 组订单状态是否同步为 `进行中`
3. C 组司机拒绝后，B 组是否能重新选择司机
4. C 组司机位置、预计到达和车辆信息是否能同步到 B 组乘车页
5. C 组司机确认送达后，B 组是否允许乘客付款
6. B 组付款评价后，C 组和管理端是否能看到订单完成
7. 司机车辆审核状态是否会影响推荐结果
8. 司机信用分是否会影响推荐结果

## 14. 开发自测计划

这里的自测是 B 组开发过程中的单元模块测试和功能验证，不等同于课程项目后续的正式测试阶段。代码组完成开发后，仍需要邀请测试组进行独立测试、集成确认和测试报告整理。

需要测试的主流程：

1. 登录乘客演示账号
2. 发布拼车需求
3. 查看推荐司机
4. 发送拼车请求后自动回到乘车页
5. 乘车页展示等待司机确认动画和 `待确认` 角标
6. mock 司机同意后，乘车页展示司机实时位置、预计到达、距离、车辆和路线信息
7. mock 行程开始后，乘车页状态更新为 `行程中`
8. mock 到达目的地后，乘车页状态更新为 `待付款`
9. 乘客付款后订单进入 `已完成`，乘车页展示付款完成页
10. 乘客可选择评价，也可以从订单页已完成列表查看轻量行程摘要

需要测试的异常流程：

- 没有填写出发地不能发布
- 没有填写目的地不能发布
- 乘车人数小于 1 不能发布
- 剩余座位为 0 的司机不推荐
- 信用分不足的司机不推荐
- 顺路度低于 60% 的司机不推荐
- 司机拒绝后，乘车页简要显示拒绝信息，并可点击“重新选择司机”回推荐页
- 订单页进行中订单点击后应回到乘车页，而不是在订单页展开实时流程
- 已取消订单不能付款
- 未付款订单不能评价
- 已完成订单不能再次付款

## 15. MVP 之后的乘客端增强规划

本节从真实乘客日常使用拼车软件的角度整理后续可做功能。以下内容不进入当前 B 组 MVP 的完成标准，只有在第五阶段自测和提交准备完成后，再根据时间选择推进。

### 15.1 用户视角缺口

下单前，真实用户通常还需要：

- 地点选择页：点击出发地 / 目的地后进入地图选点或搜索页，而不是只在主页面改文字。
- 常用地址：家、学校、公司、最近使用地点，减少每次重复输入。
- 预计信息：展示预估价格、预计路程、预计时长、可拼人数和出发时间提醒。
- 账号状态提示：实名、信用分、是否被限制发单，避免用户填完后才发现不能发单。

匹配和等待中，真实用户通常还需要：

- 司机详情：车辆、信用分、历史评价、接单率、距离和预计到达时间。
- 匹配理由：为什么推荐这位司机，例如顺路度高、座位足够、信用分高。
- 排序 / 筛选：按顺路度、价格、出发时间、信用分筛选。
- 等待超时：司机长时间未处理时，提示重新选择司机或继续等待。
- 多次请求管理：同一乘客需求下，展示已请求、已拒绝、可继续请求的司机。

行程中，真实用户通常还需要：

- 联系司机：电话或站内消息入口，真实实现依赖 A / C 组。
- 行程安全：分享行程、紧急联系人、一键求助入口，当前可先做入口和报告说明。
- 上车点确认：司机到达后提示乘客确认上车点或重新沟通。
- 取消原因：进行中取消时选择原因，并为后续信用分或申诉提供依据。

行程后，真实用户通常还需要：

- 付款详情：费用明细、支付方式、优惠券、发票入口；当前 MVP 只做模拟付款。
- 评价维度：准时、路线、态度、车辆整洁等，而不是只有星级和一句评价。
- 投诉 / 申诉：针对迟到、绕路、爽约、费用争议提交说明。
- 历史订单检索：按路线、时间、状态快速查找历史行程。

我的页面，真实用户通常还需要：

- 常用地址管理
- 钱包 / 优惠券 / 发票
- 消息通知
- 安全设置和紧急联系人
- 账号与实名信息
- 投诉记录和客服入口

### 15.2 建议优先级

| 优先级 | 功能方向 | 为什么排这个优先级 | B 组边界 |
| --- | --- | --- | --- |
| P0 | 第五阶段自测、截图、PR 准备 | 当前 MVP 已能演示，先保证提交质量 | B 组当前必须完成 |
| P1 | mock 地点选择页 + 常用地址 | 用户每天发单最频繁，且当前主页面地点入口还只是 mock 文案 | B 组可独立做 mock |
| P1 | 等待超时和重新推荐 | 司机不响应是拼车核心失败场景，比继续加静态页面更有演示价值 | B 组可先用本地状态做 |
| P1 | 司机详情和匹配理由 | 能解释推荐结果，让匹配算法在报告和演示中更可信 | B 组可展示，数据依赖 A / C |
| P2 | 修改需求和取消原因 | 覆盖用户临时改时间、改目的地、取消出行的真实场景 | B 组可做前端流程，规则需 A / C 确认 |
| P2 | 订单历史筛选和再次拼车增强 | 提升订单页真实可用性，适合报告截图 | B 组可独立做 |
| P3 | 联系司机、消息通知、安全分享 | 真实产品必需，但会牵涉用户、司机、消息和安全模块 | 需要 A / C 配合 |
| P3 | 钱包、优惠券、发票、申诉 | 真实闭环需要，但课程 MVP 不应优先扩太大 | 多组协作，先写扩展设计 |

### 15.3 下一步建议

- 当前最稳妥下一步仍是第五阶段：构建、主流程手测、截图和提交准备。
- 如果第五阶段完成后还有时间，建议 B 组优先做 `mock 地点选择页 + 常用地址`。
- 地点选择页可以先不接真实地图 API，只做搜索列表、当前位置、常用地址、最近地点和确认选择；后续真实地图接入时替换数据来源。
- 不建议 B 组先做钱包、客服、真实消息或安全中心的完整功能，这些更容易越过 B 组边界。

## 17. 当前不确定事项
